# Модуль «Справочники» (НСИ) — работающий учебный backend

**Java 21 · Spring Boot 3.5.16 · PostgreSQL 17 · JPA/Hibernate · Flyway · Swagger UI**

Демонстрационный прототип на основе ЧТЗ, презентации и согласуемой спецификации сервиса НСИ цифрового чек-листа подготовки ВС к вылету. В проект включены **35 API-методов**: 12 внешних и 23 внутренних. Разметка в Swagger соответствует именам E-01…E-12 и I-01…I-23 из Word-спецификации.

> **НЕ ДЛЯ РЕАЛЬНОЙ ЭКСПЛУАТАЦИИ В АВИАЦИИ.** Все борта, источники и длительности операций — вымышленные учебные значения. Авторизация по `X-Demo-Role` не защищена и предназначена только для локального показа.

## Быстрый запуск (проще всего)

1. Установите **Docker Desktop** и включите его (Windows / macOS), либо Docker Engine с Compose (Linux).
2. Распакуйте ZIP и откройте терминал **в папке, где находится `compose.yaml`**. На Windows можно вместо терминала запустить `start_demo_windows.bat`.
3. Запустите:

   ```bash
   docker compose up --build -d
   ```

   При первом запуске Docker скачает образы и Maven-зависимости; нужен интернет.

4. Откройте **http://localhost:8080/swagger-ui.html**.
5. Нажмите в правом верхнем углу Swagger кнопку **Authorize**. Введите `SUPERVISOR` для полного доступа, `REFERENCE_EDITOR` для редактирования или `TECHNICIAN` только для чтения. Значение без кавычек.
6. Выберите метод → **Try it out** → заполните параметры → **Execute**. Для `POST`, `PATCH`, `DELETE` указывайте новый `Idempotency-Key`, например `demo-001`.

Полезные ссылки:

- Веб-интерфейс: http://localhost:8080/ — каталоги, версии шаблонов с согласованием, аудит; роль переключается вверху страницы
- Swagger UI: http://localhost:8080/swagger-ui.html
- Машиночитаемый OpenAPI JSON: http://localhost:8080/v3/api-docs
- Health: http://localhost:8080/actuator/health
- PostgreSQL с хоста: `localhost:5433`, база `nsi`, пользователь `nsi`, пароль `nsi_demo_password`

Остановить сервер без удаления данных: `docker compose down`.

**Повторить демонстрацию с чистой базой:** `docker compose down -v` (УДАЛИТ ВСЕ изменения в демонстрационной БД), затем снова `docker compose up --build -d`.

### Разделы

| Раздел | Адрес | Что показывает и что можно сделать | Какие методы API вызывает |
|---|---|---|---|
| Сводка | `#/overview` | Счётчики каталогов, действующий шаблон с линией этапов, открытый черновик, последние события аудита | `GET /aircraft-types`, `/aircraft`, `/operation-types`, `/airports`, `/procedure-templates`, `/procedure-templates/versions/{id}`, `/audit` |
| Типы ВС | `#/types` | Список с поиском и фильтром по категории. Клик по строке открывает панель: нормативы операций и борты этого типа | `GET/POST/PATCH /aircraft-types`, `GET/POST /aircraft-types/{id}/operation-norms`, `PATCH /operation-norms/{id}` |
| Борты | `#/aircraft` | Список с поиском по бортовому номеру и фильтром по типу; создание и правка | `GET/POST/PATCH /aircraft` |
| Операции | `#/operations` | Список с поиском и фильтром по статусу; создание и правка | `GET/POST/PATCH /operation-types` |
| Аэропорты | `#/airports` | Карточки аэропортов. Клик открывает панель со стоянками | `GET/POST/PATCH /airports`, `GET/POST /airports/{id}/parking-stands`, `PATCH /parking-stands/{id}` |
| Шаблоны процедур | `#/procedures` | Слева версии, справа выбранная версия: шаги согласования, шаблоны и этапы. Черновик можно править, отправлять на согласование, утверждать или отклонять | `GET/POST /procedure-templates/versions`, `…/records`, `…/stages`, `…/submit`, `…/approve`, `…/reject` |

Линия этапов — цветная полоса в шаблоне: ширина каждого сегмента пропорциональна нормативу этапа. В черновике этапы, которые отличаются от действующей версии, отмечены точкой на линии и меткой в таблице («было 20 мин», «новый»).

### Файлы и за что они отвечают

Всё лежит в `src/main/resources/static/` и попадает в jar при сборке.

| Файл | За что отвечает |
|---|---|
| `index.html` | Каркас страницы: левая панель, верхняя строка, пустая область `#view`, куда скрипт рисует разделы; подключение шрифтов |
| `app.css` | Весь внешний вид. Цвета и радиусы — переменные в `:root` в начале файла, там же тёмная тема. Размеры заданы в `rem`, базовый размер растёт с шириной окна (правило `html { font-size: … }`) |
| `app.js` | Вся логика, один файл без зависимостей |

Блоки внутри `app.js`, сверху вниз:

| Блок | Что делает |
|---|---|
| Константы `ROLES`, `LABELS` | Список ролей и русские подписи для кодов статусов, действий и сущностей |
| `h`, `fmtDur`, `fmtDate`, `plural`, `toast` | Создание элементов, формат длительности и даты, склонения, всплывающие сообщения |
| `api`, `list` | Все запросы к серверу. Добавляет `X-Demo-Role` и новый `Idempotency-Key` для каждого изменяющего запроса, превращает ошибку сервера в текст |
| `formDialog`, `patchForm`, `drawer` | Модальная форма, форма правки (отправляет только изменённые поля) и боковая панель |
| `catalogPage`, `table` | Общий каркас страницы-списка: заголовок, фильтры, таблица, счётчик |
| `overviewPage`, `timeline` | Сводка и линия этапов |
| `typesPage`, `aircraftPage`, `operationsPage`, `airportsPage` | Страницы каталогов и их боковые панели |
| `proceduresPage`, `recordCard`, `recordForm`, `stageForm`, `stageChanges` | Версии шаблонов, согласование, правка этапов, сравнение с действующей версией |
| `auditPage` | Журнал аудита |
| `ROUTES`, `render`, `renderNav`, `renderRoles` | Список разделов, переход по адресу после `#`, перерисовка при смене роли |

Как поменять типовые вещи:

- **Цвета и стиль** — переменные в начале `app.css` (`--accent`, `--accent-2`, `--t1…--t5` для линии этапов).
- **Новый раздел** — функция страницы в `app.js` и строка в массиве `ROUTES`.
- **Новое поле в форме** — объект в массиве `fields` нужной страницы; ключ поля должен совпадать с именем в теле запроса API.

Интерфейс собран в jar, поэтому после правки файлов нужна пересборка (`docker compose up --build -d`), а в браузере — обновление с очисткой кэша (Ctrl+Shift+R). Шрифты загружаются с Google Fonts; без интернета подставляются системные.

## Что показать на согласовании (5–10 минут)

**Сценарий A — чтение работающего сервиса**

1. Выполните `GET /api/v1/references/directories` — появятся 5 справочников.
2. Выполните `GET /api/v1/references/aircraft-types` — учебные A320 и B738.
3. Выполните `GET /api/v1/references/procedure-templates/resolve?aircraft_type_code=A320&procedure_code=PRE_DEPARTURE` — целиком опубликованный шаблон и три этапа с нормативами.
4. Выполните `GET /api/v1/references/sync/manifest` — список опубликованных версий и SHA-256 снимков.

**Сценарий B — версионирование: изменённый черновик НЕ виден технику**

В моковых данных уже подготовлены:

- Справочник `OPERATION_TYPE`: `e1e2b838-c46d-5010-a959-57055aa566d5`.
- Утверждённая v1: `3de758b2-d70d-5f39-af6a-01ba4329e18d`.
- Черновик v2: `b3fb7404-97e3-5499-917c-264ef53b823d`.

В версии v1 операция `REFUEL` имеет **демонстрационные 1200 секунд**, в черновике v2 — **1500 секунд**. Это не реальные нормы обслуживания ВС.

1. В роли `TECHNICIAN`: `GET /operation-types` → REFUEL = 1200.
2. В роли `REFERENCE_EDITOR`: `GET /directories/{id}/versions/{versionId}/records`, где `{id}` и `{versionId}` — значения выше → REFUEL = 1500 в DRAFT.
3. В роли `REFERENCE_EDITOR`: `POST /directories/{id}/versions/{versionId}/submit`, тело отсутствует, `Idempotency-Key: demo-submit-1`. Статус станет `REVIEW`.
4. Попробуйте `approve` под ролью `REFERENCE_EDITOR` → **403**.
5. Смените роль на `SUPERVISOR` и вызовите `POST /directories/{id}/versions/{versionId}/approve`, `Idempotency-Key: demo-approve-1`. Статус станет `APPROVED`, а прежняя версия — `ARCHIVED`.
6. Повторите `GET /operation-types` в роли техника → REFUEL = **1500**.
7. Выполните `GET /versions/3de758b2-d70d-5f39-af6a-01ba4329e18d/status` → `usable_for_new_checklist=false`.
8. `GET /audit` под супервайзером покажет события `SUBMIT`, `ARCHIVE`, `APPROVE`.
9. Повторите approve с **тем же** `Idempotency-Key` → тот же ответ без нового изменения.

**Сценарий C — собственный справочник**

1. Под `SUPERVISOR` вызовите `POST /directories` с `Idempotency-Key: create-test-1`:

   ```json
   {"code":"DEMO_CUSTOM","kind":"GENERIC","name":"Учебный справочник","description":"Для защиты проекта"}
   ```

2. Скопируйте `directory_id` и `draft_version_id` из ответа.
3. Под `REFERENCE_EDITOR` вызовите `POST /directories/{id}/versions/{versionId}/records` с новым `Idempotency-Key`:

   ```json
   {"code":"NEW","name":"Новая запись","description":"Мок","data":{"note":"тест"}}
   ```

4. Вызовите `submit`, затем под `SUPERVISOR` `approve`, каждый раз с **новым** `Idempotency-Key`.
5. Проверьте аудит, манифест, историю версий и создание следующей DRAFT-версии.

## Структура базы

Физическая схема: `directories → reference_versions → directory_records → procedure_stages`. Отдельные таблицы `audit_log` и `idempotency_requests`.

- Каждый справочник имеет версионные снимки.
- Записи содержат `logical_id`, который сохраняется при копировании версии; физический `id` новой ревизии другой.
- Утверждённые данные нельзя редактировать через API: изменения допустимы только в `DRAFT`.
- Частичный уникальный индекс PostgreSQL гарантирует максимум одну `APPROVED`-версию на справочник.
- `approve` использует блокировку записи справочника и одну транзакцию.
- `audit_log` фиксирует старое/новое значение и роль-актора, определяемую демозаголовком.
- Idempotency-Key проверяется для каждого mutating-метода, результат хранится в PostgreSQL.
- Шаблон и его этапы версионируются вместе. Продолжительность этапа не меняется при публикации другого справочника операций.

## Локальный запуск без контейнера приложения

Можно отдельно запустить только PostgreSQL:

```bash
docker compose up -d db
mvn spring-boot:run
```

Требуются установленная Java 21, Maven и Docker. Локальный URL БД настроен в `application.yaml` на порт 5433.

## Автоматическая проверка

После старта приложения:

```bash
python smoke_test.py
```

Скрипт создаст новый уникальный учебный справочник, проверит запрет изменения техником, отправку на REVIEW, утверждение супервайзером, чтение после публикации, историю и повтор запроса с Idempotency-Key. Работает со стандартной библиотекой Python 3.

## Что в прототипе упрощено и НЕ готово для production

1. **Авторизация**. `X-Demo-Role` и `X-Demo-User` — полностью доверенные клиентские заголовки; они неприемлемы вне изолированной демонстрации. Перед внедрением нужен реальный сервис авторизации и подтверждение прав сервис-сервис.
2. **Авиационные нормативы**. Все операционные длительности условны. Настоящие регламенты требуют согласованных источников, контроля применимости, отдельного подтверждения безопасности и договорённостей с владельцем данных.
3. **Универсальная модель записей**. Типизированные авиационные сущности сейчас хранятся как валидируемый JSONB в `directory_records`, а не в отдельных физических таблицах. Такое решение упрощает MVP, но его нужно согласовать с архитектурой из Word-спецификации.
4. **Офлайн**. Есть только манифест, снимки и проверка статуса. Резервный журнал фактических операций, офлайн-приложение и курсорные диффы не реализованы.
5. **Одновременные запросы**. PostgreSQL гарантирует уникальность APPROVED; конкурентные запросы с одним Idempotency-Key могут потребовать повторного выполнения после 409. Production-перехват ошибок, блокировки и кэширование требуют отдельной нагрузки и тестирования.
6. **ETag**. Поддержано условное обновление метаданных справочника через `If-Match`, но не все операции поддерживают optimistic concurrency.
7. **Каталоги**. В демонстрации нет фоновых задач, полноценного UI, внешних событий и интеграций.
8. **Ограничения импорта**. Есть JSON UPSERT и `dry_run`; загрузка Excel/CSV и детальные ошибки по строкам пока не реализованы.
9. **Тестирование**. Проект подготовлен для локальной сборки, но в среде создания архива не было Maven, PostgreSQL и Docker; поэтому реальная сборка и интеграционный прогон здесь не выполнялись. Для проверки запускайте `docker compose up --build` и `python smoke_test.py` на машине с Docker.

## Для согласования

Прямо демонстрируются `BT-01` (единый API), `BT-02` (только актуальная APPROVED), `BT-03` (аудит), роли из `BT-05`, DRAFT/REVIEW/APPROVED/ARCHIVED, diff, импорт и часть офлайн-механизма из `BT-04`.

Для следующего этапа работы: подключить настоящий auth-service, обсудить разделение схемы JSONB и отдельных таблиц, добавить контракты команды чек-листа и согласовать работу с резервным журналом.
